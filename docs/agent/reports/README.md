# 报告目录

本目录存放任务/阶段/调研/发布的实际结果报告。报告面向“下一个接手的人”，必须包含可复现证据，而不是只写“已完成”。

- 文件名：`<phase>-<area>-<slug>-report.md`，如 `p0-input-stylus-spike-report.md`
- 调研：`spike-<slug>-report.md`
- 发布：`release-<version>-report.md`
- 缺陷专项：`bug-<id>-<slug>.md`

所有报告使用 Markdown，不得只存在于对话或提交信息。

---

## 1. 报告状态

| 状态 | 含义 |
|---|---|
| `Completed` | 验收通过，证据齐全 |
| `Partial` | 部分完成，明确未完成项与影响 |
| `Blocked` | 等待决策/依赖/设备/用户 |
| `Cancelled` | 停止，需说明原因与替代 |
| `Failed` | 尝试后不可行，需记录证据与后续 |

`Partial`/`Blocked` 不等于完成；不要用模糊措辞掩盖。

---

## 2. 报告模板

```markdown
# 报告：<任务/阶段>

- 状态：Completed / Partial / Blocked / Cancelled / Failed
- 日期：
- Agent/负责人：
- 关联计划：
- 关联需求：
- 关联决策：
- 关联风险：

## 1. 摘要

2–5 句话说明结果、影响和是否可继续。

## 2. 范围

实际做了什么；与计划的偏差。

## 3. 完成内容

- 模块/文件/接口；
- 用户可见行为；
- 数据/格式/ABI 变更。

## 4. 未完成/偏差

- 未完成项及原因；
- 与计划/需求的差异；
- 临时方案/技术债（必须可追踪）。

## 5. 验证与证据

### 自动化

```bash
<命令>
```
结果：通过/失败，关键输出。

### 手工/设备

| 设备 | OS | 构建 | 场景 | 结果 |
|---|---|---|---|---|
| ... | ... | ... | ... | ... |

### 性能

| 指标 | 结果 | 环境/样本 |
|---|---|---|
| ... | ... | ... |

## 6. 文档更新

- 需求/决策/格式/UX/架构/风险/计划；
- 未更新项及原因。

## 7. 风险与遗留

- 新发现风险（是否已登记 `10`）；
- 已知限制；
- 数据/兼容性影响；
- 需要用户确认的事项。

## 8. 结论与下一步

- 是否满足退出标准；
- 建议的下一任务/阶段；
- 阻塞项。
```

---

## 3. 证据要求

- 命令必须是实际执行过的，包含工作目录/构建类型（必要时）；
- 测试结果说明通过/失败数量，不只写“全过”；
- 性能数据包含设备、OS、构建模式、fixture、样本数；
- UI 变更附截图/录屏路径或说明；
- 格式/迁移附 fixture 与命令；
- 缺陷附复现步骤、严重度、影响；
- 不粘贴密钥、用户正文、个人路径。

---

## 5. 报告纪律

1. 完成/阻塞/取消都要写，不只写成功。
2. 报告与计划互相链接；计划状态同步更新。
3. 证据优先于形容词；没有证据就写“未验证”。
4. 不隐瞒失败/跳过/已知缺陷。
5. 报告中的结论若改变范围/架构/格式，必须同步 `09`/`01`/`03` 等文档。
6. 报告不是流水账；突出决策、影响和下一步。
7. 后续 Agent 接手前必须阅读相关报告，但不盲信；以仓库实际状态为准。
