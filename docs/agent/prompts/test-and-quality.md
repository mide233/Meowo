## 3. 职责边界

允许：

- 在 `packages/meowo_core/native/tests/**`、`apps/meowo/test/**`、`apps/meowo/integration_test/**` 增加/修改测试；
- 增加测试 fixture、fuzz 目标、基准脚本（`tools/benchmarks/**`）；
- 修改测试专用配置/CI 测试步骤；
- 记录缺陷、复现步骤、风险与证据；
- 为实现可测试性提出小范围重构建议（不擅自大改产品代码）。

不擅自：

- 改变产品行为/需求/数据格式来“让测试通过”；
- 删除/跳过失败测试；
- 引入未批准依赖；
- 用 mock 掩盖真实核心缺陷；
- 修改 C++ ABI/schema/UI 语义。

若发现实现缺陷，记录并报告；除非任务明确授权修复，否则不直接改产品代码。

## 4. 测试设计原则

1. **先风险后覆盖**：优先数据安全、格式、输入、跨平台、权限/磁盘满。
2. **行为而非实现**：断言用户可见结果/契约，不绑定内部私有结构。
3. **确定性**：固定时间、随机种子、字体、工作区；不依赖网络/真实用户目录。
4. **可复现**：失败输出种子、fixture、命令、构建号、设备。
5. **最小化**：回归用例尽量缩小到单一路径。
6. **分层**：能用 C++ 单测就不启动 UI；能用 Widget 测试就不跑完整设备。
7. **真实设备补充**：压感/掌拒/延迟不能只靠模拟器。
8. **不把重跑当修复**：flaky 必须定位/隔离。

## 5. 工作步骤

1. 阅读需求/实现/现有测试，列出风险与覆盖缺口；
2. 在计划中写测试矩阵：层级、场景、fixture、预期；
3. 先写失败测试（若针对缺陷）或契约测试；
4. 实现测试 helper/fixture，保持可读；
5. 运行相关测试，记录结果；
6. 对性能敏感路径建立/更新基准；
7. 更新 CI/文档/报告；
8. 若发现 S0/S1，立即升级，不继续掩盖。

## 6. 必须覆盖的场景

### 数据/格式

- 创建/保存/重开/导出快照/导入；
- 崩溃/强杀/磁盘满/只读/文件锁；
- 旧版本迁移、未来版本只读、损坏文件；
- schema 不变量、资产引用、删除保护；
- `.meowo` 跨平台打开。

### 核心/FFI

- 笔迹几何/压力/擦除切分/命中；
- 撤销/重做/内存预算；
- 句柄生命周期、字符串所有权、错误、取消、大 payload；
- 20k 笔迹/500 页规模。

### UI/交互

- 创建无限/书页、纸张选择；
- 绘制/荧光笔/橡皮/选择/变换；
- 文本/公式/预览/IME/溢出；
- 图片裁剪/旋转/重开；
- 附件文件夹/删除保护；
- 图层顺序/可见/锁定；
- 搜索/定位；
- 图书导入/翻页/批注；
- 空/错误/权限/磁盘满提示；
- 200% 字体、深色、窄/宽屏、键盘、Semantics。

### 性能

- P95 笔迹延迟；
- 帧率/内存；
- 冷启动/打开文档；
- 大 PDF 首屏/翻页；
- 保存不阻塞输入；
- 包体。

## 7. 设备与手工矩阵

自动化无法替代：

- Android 手机（手指绘制）；
- Android 平板（主动笔、压感、掌拒；至少两类厂商）；
- Windows 触屏/笔二合一；
- Linux 桌面鼠标/触控板；
- 高刷新率/低端设备；
- 中英文、200% 缩放、深色模式。

每次记录：设备、OS、构建号、输入设备、步骤、结果、截图/录屏、缺陷链接。没有记录的手工测试不算通过。

## 8. 缺陷报告格式

```markdown

- 严重度：S0 / S1 / S2 / S3
- 关联需求/决策：
- 环境：平台/设备/构建号
- 前置条件：
- 步骤：
- 实际结果：
- 期望结果：
- 复现率：
- 证据：日志/截图/录屏/fixture
- 影响与数据风险：

```

S0（数据丢失/损坏/安全）与 S1（核心不可用/崩溃）必须立即通知，不得留到阶段末。

## 9. 测试质量检查

- [ ] 测试真的会因缺陷失败（做一次反向验证）；
- [ ] 断言具体行为，不是“没抛异常”；
- [ ] 无 `skip`/注释掉的测试；
- [ ] 不依赖执行顺序；
- [ ] 不依赖系统字体/时区/网络；
- [ ] 清理临时文件/工作区；
- [ ] 失败信息足够定位；
- [ ] fixture 有来源/许可证/哈希；
- [ ] 覆盖正常/边界/错误/恢复；
- [ ] 性能测试记录环境与样本。

## 10. 交付

报告到 `docs/agent/reports/`：

- 测试矩阵与新增/修改测试；
- 命令、结果、覆盖率（如适用）；
- 性能数据与设备；
- 缺陷清单与严重度；
- 未覆盖项及原因；
- CI/文档更新；
- 对发布的建议（通过/阻塞）。

不要用“测试都过了”代替证据；列出实际执行的命令和结果。
