## 3. 不可协商的约束

1. Flutter 不直接打开 `.meowo`，所有文档/存储/几何通过 `meowo_core`。
2. C ABI 稳定、显式所有权、无异常穿越边界。
3. `.meowo` 是单文件 SQLite；格式变更必须版本化、迁移、备份、测试。
4. 数据安全优先：不得伪造保存成功，不得静默覆盖损坏/未来版本文件。
5. 1.0 范围以需求和决策为准；未确认的 OQ 不得用私有实现“先上了再说”。
6. 未经批准不得引入 AGPL/GPL/未知许可证依赖。
7. 测试与实现同交；不得跳过/删除测试来“通过”。
8. 计划、报告、决策必须写入 `docs/agent/` 的 Markdown，不得只存在于对话。
9. 不自动 commit/push，除非用户明确授权。
10. 不执行未确认的破坏性操作，不接触真实用户数据。

## 4. 工作流程

### 4.1 启动

1. 检查工作区、分支、未提交变更、工具链；
2. 阅读文档与现有代码，列出现状与缺口；
3. 把阶段目标拆成 3–8 个可独立验收的切片；
4. 在 `docs/agent/plans/` 创建/更新阶段执行计划，包含每个切片的：
   - 范围与非目标；
   - 涉及模块/文件；
   - 数据/ABI/格式/UI 影响；
   - 测试与验收；
   - 风险与回滚；
   - 依赖顺序。
5. 先做风险最高、最能证伪架构的切片（通常是格式/FFI/输入/渲染），不要先铺 UI。

### 4.2 每个切片

1. 写/更新任务计划（可以是阶段计划的子节，但必须可追踪）；
2. 先定义数据契约与失败路径；
3. 实现最小端到端路径：核心 → FFI → Dart → UI；
4. 补单元/契约/Widget/集成测试；
5. 跑格式化、静态检查、相关测试；
6. 自审：范围、错误路径、资源生命周期、性能、可访问性、文档；
7. 更新计划状态，提交给审查 Agent（如可用）；
8. 记录证据到报告。

### 4.3 集成与收尾

- 每个切片合并前保证主分支可构建；
- 处理跨切片接口漂移，更新 ABI/格式文档；
- 运行阶段退出标准；
- 写阶段报告：完成/未完成、证据、性能、风险、下一阶段建议；
- 若有未关闭 OQ，明确标注阻塞项，不擅自决定。

## 5. 任务拆分原则

好的切片：

- 有用户可观察结果；
- 能独立测试；
- 尽量少跨团队/文件；
- 失败可回滚；
- 不依赖未确认的外部条件。

避免：

- “先写完全部模型再写 UI”；
- “先做设置页占位”；
- 为未来功能预埋大量未使用抽象；
- 同时改格式、ABI、UI 和构建系统；
- 把测试留到最后。

## 6. 子 Agent 协作

需要并行时：

- 给每个子 Agent 自包含提示：必读文档、范围、非目标、文件边界、验收、报告路径；
- 核心/应用/测试可并行，但同一文件/同一 schema/同一 ABI 头文件只能一个负责人；
- 不让子 Agent 自行扩大范围或改决策；
- 主 Agent 复核所有产出，运行集成测试后再合并；
- 交接写入计划/报告，不依赖聊天记忆。

推荐分工：

- C++ 核心 Agent：`packages/meowo_core/native/**`；
- Flutter Agent：`apps/meowo/**`；
- 测试 Agent：测试与基准，不擅自改产品行为；
- 审查 Agent：只审查，不改代码（除非明确要求修复）。

## 7. 质量门禁

每个切片至少：

- [ ] 相关 C++ 单元测试通过；
- [ ] FFI 契约测试通过（若改 ABI）；
- [ ] Dart 单元/Widget 测试通过；
- [ ] 关键路径集成测试或手工记录；
- [ ] 格式/迁移测试（若改 schema）；
- [ ] 性能基准（若在热路径）；
- [ ] `flutter analyze`/编译器无新增警告；
- [ ] 文档/计划更新；
- [ ] 无调试代码、跳过测试、硬编码路径。

阶段完成必须满足 `06-roadmap.md` 的退出标准与 `05-quality-and-test-strategy.md` 的 DoD。

## 8. 升级与停止条件

立即停止并询问用户：

- 需要改变 1.0 范围/文件格式/数据模型；
- 许可证/分发模式不清；
- 可能数据丢失或不可逆迁移；
- 发现文档冲突且无法按权威顺序解决；
- 关键硬件/平台不可用；
- 出现 S0 缺陷。

提问格式：问题 → 选项 → 推荐 → 影响 → 需要用户做的决定。
