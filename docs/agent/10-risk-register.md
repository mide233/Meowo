## 1. 使用方式

风险评分：

- **可能性（L）**：低 / 中 / 高；
- **影响（I）**：1（轻微）– 5（数据丢失、项目不可交付、许可证不可用）；
- **等级**：`高`（I≥4 或 L×I≥12）、`中`（L×I 6–11）、`低`（≤5）。

风险不是待办事项。每项必须有：

- 触发信号（何时升级）；
- 缓解措施（降低概率/影响）；
- 责任人角色（不是具体个人）；
- 关联阶段/需求；
- 复审结论。

处理策略：**避免**（改方案）、**降低**（验证/隔离/测试）、**转移**（商业授权/保险）、**接受**（记录并准备应急）。

> 当前最高风险：EPUB 许可证/引擎、数据损坏/丢失、笔输入延迟与跨平台压感、格式/ABI 早期不稳定、范围膨胀。

## 3. 重点风险详述

### R-001 · EPUB 引擎许可证与能力

**为什么重要**：EPUB 固定分页是 1.0 明示需求，但成熟引擎（如 MuPDF）通常为 AGPL 或商业授权；宽松方案需要自研 HTML/CSS 分页，工作量和保真风险都很高。若 Phase 4 才发现不可行，会推翻路线图与宣传。

**缓解**：

1. Phase 0 完成 OQ-001，书面记录分发模式、许可证义务、成本；
2. BookEngine 抽象，PDF 与 EPUB 解耦；
3. 准备 D 方案（1.0 仅 PDF）并明确需要用户批准的范围变更；
4. 若采用快照，导入时固化分页与渲染版本，保留原始 EPUB；
5. 不在主线合入未批准许可证的二进制。

**触发**：候选引擎无法交叉编译/分页质量不可接受/许可证与分发冲突/商业授权超预算。

**应急**：缩减 1.0 为 PDF，EPUB 延后；或调整项目许可证；不得静默使用未授权库。

---

### R-002 · 笔迹延迟与压感跨平台

**为什么重要**：这是产品核心卖点。Flutter 事件管线、平台笔事件、FFI、渲染管线和设备刷新率都可能成为瓶颈；模拟器无法代表真实体验。

**缓解**：

1. Phase 0 在目标 Android 平板/Windows 二合一上测端到端延迟；
2. 输入事件直接进入核心，进行中笔迹独立渲染，不等待完整文档提交；
3. 建立 P50/P95/P99 基线，优化有数据支撑；
4. 保留降级路径（降低预测/平滑复杂度、限制同屏点数），但不牺牲正确性；
5. 真机矩阵纳入每个发布候选。

**触发**：参考设备 P95 连续两个里程碑 > 50 ms；压感事件缺失/抖动；高刷新率设备锁帧。

**应急**：调整渲染分层/减少每帧工作；与用户确认参考设备定义；必要时限制宣传指标。不得用假插值掩盖输入延迟。

---

### R-004 · 数据丢失/损坏

**为什么重要**：单文件承载长期笔记，一次损坏可能不可恢复。SQLite 很稳健，但错误的事务、WAL 复制、迁移、磁盘满、文件锁和多实例都可能破坏。

**缓解**：

1. WAL + 事务 + 外键 + 完整性检查；
2. 保存失败保留旧版本，绝不覆盖为部分写入；
3. 迁移前备份，失败回滚；
4. 崩溃/磁盘满/权限/锁注入测试；
5. 导出使用一致性快照；
6. 打开时验证，未来版本只读/拒绝写；
7. 不在 UI 伪造“已保存”。

**触发**：任何 S0；打开失败率上升；用户报告内容消失；WAL 文件异常。

**应急**：停止写入、保留现场、提供备份/恢复工具；发布 hotfix 前加回归测试。

---

### R-005 · 格式/ABI 早期不稳定

**为什么重要**：Phase 1–3 会不断发现模型缺口。若每次直接改 schema/ABI 而不迁移，旧文档和测试 fixture 会失效；若过早冻结错误设计，又会长期背负。

**缓解**：

1. Phase 0 用真实切片验证核心表/JSON/FlatBuffers 边界；
2. 版本化 schema、payload、ABI；
3. 每次变更提供迁移与旧 fixture；
4. 1.0 前允许 breaking，但必须有升级路径与备份；
5. 不把 UI 临时状态写入格式。

**触发**：连续多个任务修改同一 schema；旧 fixture 无法打开；Dart/C++ 对字段语义理解不一致。

**应急**：暂停新增格式功能，先补迁移/契约测试与设计评审。

---

### R-008 · Markdown/LaTeX/IME

**为什么重要**：完整 CommonMark/GFM、数学公式、源码/预览、中文 IME、选区/撤销组合在一起，复杂度容易失控；渲染不一致会直接影响笔记可信度。

**缓解**：

1. 明确语法边界（TXT-001/002），不承诺完整 HTML/远程资源；
2. 使用成熟解析器 + 本地渲染，公式范围限定；
3. 源编辑与预览分离，提交时整体进入撤销；
4. Android/Windows/Linux 输入法真机测试；
5. 大文档分段渲染与缓存；
6. 恶意输入清洗与 fuzz。

**触发**：解析器无法满足 GFM 子集；IME 丢字/光标错位；预览卡顿；公式崩溃。

**应急**：缩减公式/HTML 子集并更新需求；切换渲染库需走依赖/许可证评审。

---

### R-010 / R-020 · 图书引擎安全与构建

**为什么重要**：PDF/EPUB 是不可信输入，解析器漏洞可导致任意代码执行/崩溃；MuPDF 交叉编译、包体与 AGPL 义务也可能拖慢发布。

**缓解**：

1. Linux/Android 构建已验证；Windows 构建仍需补验；
2. 固定版本、跟踪 CVE、及时升级；
3. 在隔离进程/受限环境渲染，设置超时/内存上限；
4. 导入前限制文件大小/页数/解压比；
5. fuzz 与畸形样本测试；
6. 许可证与第三方声明。

**触发**：高危 CVE 无修复；渲染进程可被拖垮；包体超预算。

**应急**：禁用受影响格式/功能，发布安全更新；必要时更换引擎。

---

### R-011 · EPUB 批注漂移

**为什么重要**：EPUB 是流式格式，不同字体/窗口/引擎版本会重排。若批注只记录“第 3 页某个坐标”，换设备就可能错位。

**缓解**：

1. 导入时生成固定分页快照（优先 PDF 或等价固定布局），批注锚定快照页；
2. 保留原始 EPUB 供重排/重导入；
3. 记录引擎 ID/版本与快照哈希；
4. 不承诺跨引擎分页一致；UI 说明来源；
5. 若未来支持重排，需设计文本锚点映射，不能复用页坐标。

**触发**：同文档不同设备页码/内容不一致；引擎升级后批注错位。

**应急**：停止对旧快照的原地重排；提供重新导入/迁移工具；保留原文件。

---

### R-016 · 无真实笔的 CI

**为什么重要**：自动化能验证事件逻辑，但不能验证压感、掌拒、屏幕刷新和手感。若只在模拟器测试，发布时才发现问题。

**缓解**：

1. 明确手工设备矩阵与发布门禁；
2. 录制真实输入事件做回放测试；
3. 输入策略/几何逻辑纯单测；
4. 每个里程碑至少一台真实笔设备；
5. 报告中记录设备/OS/构建。

**触发**：连续阶段无真机记录；用户反馈模拟器无法复现。

**应急**：暂停相关发布，补设备验证；不得用模拟器结果宣称达标。

---

### R-018 · 范围膨胀

**为什么重要**：项目初始需求已经很大，任何“顺手加一个”的功能都会推迟核心体验与发布。长期项目最常见失败原因是范围失控，而不是技术难题。

**缓解**：

1. 明确非目标与阶段退出标准；
2. 新需求必须进需求文档并确认阶段；
3. 计划中记录“发现但不在范围”；
4. 每个阶段只承诺可验证的垂直切片；
5. 项目负责人定期冻结范围。

**触发**：连续增加未确认功能；阶段多次延期；核心功能被“以后再说”。

**应急**：范围评审，砍非核心项，更新路线图；不得静默降低 MUST 验收。
