# 08 · Agent 工作协议

- 状态：Baseline
- 版本：v0.1.0
- 最后更新：2026-10-19
- 适用对象：所有参与 Meowo 的 AI Agent、子 Agent 与人类协作者

---

## 1. 目的

本协议规定 Agent 如何阅读项目、制定计划、修改代码、验证结果、记录决策和向用户汇报。目标是：

- 任何 Agent 都能从文档恢复上下文，不依赖聊天记忆；
- 计划、范围、验收和证据都可追溯；
- 不因并行/交接造成重复、冲突或数据损坏；
- 不静默扩张范围，也不静默降低质量。

**核心规则：没有写入 `docs/agent/plans/` 的任务计划，不开始实现。**

---

## 2. 开始任何任务前

### 2.1 必读文档

按顺序阅读：

1. `docs/agent/README.md`；
2. `docs/agent/00-product-charter.md`；
3. `docs/agent/01-functional-requirements.md`；
4. `docs/agent/09-decisions-and-open-questions.md`（尤其 `Accepted` 与当前任务相关的 `Open`）；
5. `docs/agent/03-document-format.md`；
6. `docs/agent/02-technical-architecture.md`；
7. `docs/agent/04-ux-interaction-spec.md`；
8. `docs/agent/05-quality-and-test-strategy.md`；
9. `docs/agent/07-engineering-conventions.md`；
10. 当前阶段/任务对应的 `docs/agent/plans/*.md`；
11. 与任务相关的历史 `docs/agent/reports/*.md`。

角色提示词在 `docs/agent/prompts/`，只用于补充工作方式；与上述文档冲突时以主文档为准，并立即报告冲突。

### 2.2 环境检查

- 确认当前工作目录、分支/工作树、未提交变更；
- 阅读项目根 `README.md` 的实际构建命令；
- 检查依赖、工具链、设备是否可用；
- 若仓库尚为空或未初始化，先确认是否处于 Phase 0，不得擅自假设结构；
- 不覆盖或删除不属于当前任务的用户/其他 Agent 变更；先检查 `git status`（若已初始化）和文件时间/内容。

### 2.3 任务理解

在写计划前，用一句话写下：

- 用户要的可观察结果；
- 不在本次范围内的内容；
- 关联需求 ID / 决策 ID；
- 验收方式；
- 最大风险。

若需求含糊且影响实现，先问用户或记录 OQ；不要用“合理猜测”直接实现大范围功能。

## 3. 标准工作流

```text
 Orient（阅读/检查）
   ↓
 Plan（写入 docs/agent/plans/*.md）
   ↓
 Confirm（范围/风险，必要时问用户）
   ↓
 Smallest vertical slice（数据→核心→FFI→UI→测试）
   ↓
 Verify（自动化 + 手工/性能）
   ↓
 Self-review（对照需求/规范）
   ↓
 Update docs（需求/决策/格式/计划/报告）
   ↓
 Report（证据、遗留、下一步）
```

### 3.1 Orient

- 搜索现有实现、测试、文档，避免重复造轮子；
- 找出相似功能的分层与模式；
- 确认当前代码是否已偏离文档（若有，先记录，不静默迁就）。

### 3.2 Plan

在 `docs/agent/plans/` 创建或更新任务计划，必须包含：

- 标题、状态、日期、负责人/Agent；
- 关联需求/决策/风险；
- 目标与非目标；
- 当前状态与前置条件；
- 任务拆分（可独立验证的步骤）；
- 数据/ABI/格式/UI 影响；
- 测试与验收标准；
- 风险、回滚、未决问题；
- 进度记录（完成/阻塞）。

计划是活文档：开始、遇到阻塞、范围变化、完成时都要更新。不得只写在聊天或提交信息里。

### 3.3 最小垂直切片

优先实现一条端到端可验证的路径，而不是先铺满所有层：

1. 数据模型/格式；
2. C++ 核心逻辑与测试；
3. C ABI / Dart 绑定；
4. 应用状态/控制器；
5. UI 与交互；
6. 保存/重开/错误路径；
7. 集成测试或手工验收。

切片完成后先验证，再扩展。避免“先写 5000 行，最后一起调”。

### 3.4 测试与验证

- 按 `05-quality-and-test-strategy.md` 选择测试层级；
- 核心逻辑必须有 C++ 单元测试；
- FFI 变更必须有契约/生命周期测试；
- UI 关键路径有 Widget/集成测试；
- 格式/迁移变更必须有 fixture 与迁移测试；
- 性能敏感变更必须提供基准数据；
- 手工验证记录设备、构建、步骤、结果；
- 失败就是失败，不把“偶尔出现”当通过。

### 3.5 自审

提交/汇报前逐项检查：

- [ ] 是否只改了任务范围？
- [ ] 是否符合 Accepted 决策与 MUST 需求？
- [ ] 是否引入未批准依赖/许可证？
- [ ] 错误/空/权限/磁盘满/损坏路径是否处理？
- [ ] 是否有资源/句柄泄漏？
- [ ] 是否更新了格式/ABI/迁移文档？
- [ ] 测试是否覆盖回归点且没有跳过？
- [ ] 是否留下调试代码、临时开关、硬编码路径？
- [ ] 文档链接/命令是否有效？

### 3.6 更新文档

以下变更必须同步文档：

| 变更 | 必须更新 |
|---|---|
| 功能/范围/验收 | `01-functional-requirements.md`、相关计划 |
| 架构/模块/依赖 | `02-technical-architecture.md`、`07-engineering-conventions.md` |
| 文件格式/schema/FlatBuffers | `03-document-format.md` + 迁移测试 |
| 交互/视觉/输入 | `04-ux-interaction-spec.md` |
| 测试门槛/设备矩阵 | `05-quality-and-test-strategy.md` |
| 阶段/顺序/退出标准 | `06-roadmap.md` |
| 决策/取舍/未决问题 | `09-decisions-and-open-questions.md` |
| 风险变化 | `10-risk-register.md` |
| 本次工作结果 | 计划状态 + `reports/` |

不要用代码注释代替上述文档。

### 3.7 报告

任务结束（完成/阻塞/取消）写报告到 `docs/agent/reports/`，命名与格式见 `reports/README.md`。报告必须包含可复现证据，而不是“应该可以”。

## 4. 权威与冲突

权威顺序：

1. 用户当前明确指令；
2. `09` 中 `Accepted` 决策；
3. `01` 中 MUST 需求；
4. `03` 格式与 `02` 架构；
5. `04`/`05`/`07` 等规范；
6. 任务计划、代码、历史报告。

处理冲突：

1. 停止有争议的实现；
2. 在 `09` 新增/更新决策或 OQ，说明冲突与影响；
3. 若影响范围/数据/许可证，向用户确认；
4. 获得结论后再继续，并在计划中记录。

不得以“代码已经这样写了”为由保留偏离；也不得为了通过测试而修改需求语义。

---

## 5. 范围纪律

### 5.1 允许

- 完成计划内、与需求直接相关的实现与测试；
- 为可测试性做小范围重构（不改变外部行为）；
- 修复阻塞当前任务的缺陷（记录在计划中）；
- 更新必要文档。

### 5.2 不允许

- 顺手加入未列出的功能、设置、依赖、平台；
- 改变文件格式/ABI/数据结构而不更新文档与迁移；
- 用占位实现冒充完成（如假保存、假搜索、假导入）；
- 为赶进度删除/跳过测试；
- 引入 AGPL/GPL/未知许可证依赖（OQ-001 未批准前）；
- 修改用户未要求的设计方向/品牌；
- 大规模无关格式化/重命名；
- 未经许可执行破坏性 git/文件操作；
- 把计划只写在对话中。

### 5.3 范围膨胀的处理

发现“必须顺手做”的内容时：

1. 写入计划的“发现/后续”；
2. 评估是否阻塞当前验收；
3. 若阻塞，说明原因并请求扩大范围；
4. 若不阻塞，不实现，留待新任务。

## 6. 需要立即停下并询问用户的情况

- 许可证/分发模式不明确，且任务需要相关依赖；
- 需要改变 1.0 范围、文档类型、文件格式或数据模型；
- 可能造成数据丢失/不可逆迁移；
- 需要真实用户数据/密钥/账号；
- 现有文档互相矛盾且无法按权威顺序解决；
- 需要购买/注册服务、签名证书、商店账号；
- 硬件/平台不可用导致无法验证关键用户路径；
- 测试暴露 S0（数据损坏/安全）问题；
- 用户指令与 Accepted 决策冲突。

询问时给出：问题、选项、推荐、影响、需要的决定。不要只问“怎么办”。

---

## 7. 多 Agent 与并行工作

### 7.1 基本原则

- 一个任务一个负责人；并行任务必须在计划中列出边界与文件/模块归属。
- 不同 Agent 不同时修改同一核心文件/同一 schema/同一 ABI 头文件。
- 文档冲突优先于代码冲突：先确定权威表述，再合并。
- 共享分支保持可构建；大功能用独立 worktree/分支。

### 7.2 工作树

- 在仓库根目录之外创建 worktree 时，记录路径与用途；
- 每个 worktree 只服务一个任务/阶段切片；
- 合并前 rebase/同步主分支并重跑受影响测试；
- 删除 worktree 前确认无未提交变更；
- 不把构建产物/临时文件带入主工作树。

### 7.3 交接

交接必须提供：

- 计划链接与当前状态；
- 已完成/未完成清单；
- 关键文件与决策；
- 测试命令与最近结果；
- 已知问题/风险；
- 下一步建议。

接手的 Agent 必须实际读取文件与测试，不盲信交接描述。

### 7.4 子 Agent

- 子 Agent 的任务提示必须包含：必读文档、范围、非目标、验收、报告位置。
- 子 Agent 不自动获得主 Agent 的隐含上下文；不要假设它知道当前决策。
- 子 Agent 的产出由主 Agent 复核后再合并。
- 不让多个子 Agent 并行写同一文件。

---

## 8. 数据与操作安全

- 真实用户文档、个人路径、密钥不得进入仓库、测试或日志。
- 测试使用临时工作区，结束清理；不操作用户资料库。
- 迁移/批量修改前备份；提供 dry-run（可行时）。
- 不运行不可逆删除命令（`rm -rf`、清空工作区）除非用户明确授权且路径已确认。
- 不强制 push、不重写共享历史、不删除他人分支。
- 导入/解析不可信文件在隔离进程，限制资源。
- 崩溃/错误不得覆盖原文件；保存失败必须保留旧版本。
- 发现数据损坏时停止写入，保留现场，报告用户。

---

## 9. 提交与交付

- 默认不自动 commit/push，除非用户或任务明确授权。
- 若授权提交：遵循 `07-engineering-conventions.md` 的 Conventional Commits，一个逻辑变更一个提交。
- 交付说明包含：变更文件、测试命令/结果、手工验证、文档更新、遗留风险。
- 不把“代码已写”当交付；必须能构建、测试、运行。
- 未完成的任务明确标记 `Blocked`/`Partial`，不伪装完成。

---

## 10. Definition of Done（Agent 视角）

任务完成必须同时满足：

- [ ] 计划已建立并更新为完成；
- [ ] 范围与需求/决策一致；
- [ ] 代码可构建、可运行；
- [ ] 自动化测试通过，手工验收有记录；
- [ ] 错误/边界/恢复路径验证；
- [ ] 格式/ABI/迁移/性能影响已处理并记录；
- [ ] 文档已同步；
- [ ] 报告已写入 `docs/agent/reports/`；
- [ ] 无未解决 S0/S1，遗留问题明确；
- [ ] 工作区无无关/临时文件。

未满足项必须在报告中逐条列出，不得省略。

---

## 11. 报告格式（摘要）

完整模板见 `reports/README.md`。至少包含：

```markdown
# 报告：<任务>
- 日期 / Agent / 计划链接
- 状态：Completed / Partial / Blocked
- 范围
- 完成内容
- 未完成/偏差
- 测试与证据（命令、结果、设备）
- 性能数据（如适用）
- 文档更新
- 风险与后续
```

报告面向“下一个接手的人”，不是写给自己的流水账。

---

## 12. 提示词使用

- 角色提示词：`prompts/` 下对应文件；
- 功能任务：使用 `prompts/feature-task-template.md` 填充占位符；
- 提示词不得覆盖主文档，不得自行增加需求；
- 每次任务把“必读文档 + 当前计划 + 范围 + 验收”放进提示，避免依赖历史对话；
- 若提示词与实际文档冲突，报告冲突并以文档为准。

---

## 13. 快速检查清单

开始前：

- [ ] 读过必读文档与相关计划/报告；
- [ ] 知道需求 ID、决策 ID、验收标准；
- [ ] 工作区干净/变更已识别；
- [ ] 依赖与设备可用；
- [ ] 已写计划。

结束前：

- [ ] 测试通过并有证据；
- [ ] 手工/性能验证完成；
- [ ] 文档/计划/报告更新；
- [ ] 无临时/调试残留；
- [ ] 范围未膨胀；
- [ ] 用户可据此继续。
